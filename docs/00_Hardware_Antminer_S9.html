1. The board

The Antminer S9 was a Bitcoin mining machine. Its control board (marked AntMiner ControlBoard XC7010 V1.01) was the "brain" that talked to the hash boards. Without the hash boards it is a very capable small computer with an FPGA inside: a cheap development board.

2. The Zynq chip: two worlds in one

A Zynq is two different things glued together on one piece of silicon:

PS = Processing System (the ARM side) Two ARM Cortex-A9 processors (like an old smartphone), plus a fixed set of peripherals: memory controller, Ethernet, SD card, UART, I2C, USB, timers. This is where Linux and your programs (Python, C) run. Its wiring is fixed: you configure it, you cannot change it.
PL = Programmable Logic (the FPGA side) About 17,600 logic cells (LUTs), 80 multipliers (DSP), 2.1 Mbit of block memory. Empty at power-on. You describe hardware (Verilog / VHDL / Vivado blocks), and a bitstream (.bit file) wires it up. Everything runs truly in parallel, at the speed of real circuits.
Arduino comparison An Arduino has one small processor. The Zynq has two big processors (the PS) and a whole field of logic you can wire yourself (the PL). A program on the PS is like an Arduino sketch. A design in the PL is like building your own chip.

3. How the two worlds talk

LinkDirectionWhat it is used for
M_AXI_GP0 (AXI bus)ARM → FPGAThe ARM reads and writes registers inside your FPGA design. Addresses start at 0x4000_0000. Example: an AXI GPIO at 0x4120_0000; writing 5 there turns LEDs 0 and 2 on.
FCLK0..3 (clocks)ARM → FPGAClock signals made by the ARM side. Ardzy uses FCLK0 = 100 MHz. The board has no separate FPGA crystal, so your design takes its clock from here.
IRQ_F2P (interrupts)FPGA → ARMYour logic can "ring a bell" for the program (Ardzy: the UIO driver + UIO.wait() in Python).
HP / ACP portsFPGA → memoryFast direct memory access (DMA) for big data like samples or video. Advanced.
EMIObothRoute PS peripherals (extra UART, SPI, I2C) through FPGA pins.

From Python on the board, a register is just a memory address:

from ardzy import MMIO
gpio = MMIO(0x41200000)      # the base address shown in Vivado's Address Editor
gpio.write(0, 0b0101)        # LEDs 0 and 2 on
print(gpio.read(0))

7. The memory chips (DDR3)

DDR3 memory needs exact settings: how many address lines it has, and timing values in nanoseconds. The first boot stage writes these into the memory controller (registers at 0xF800_6000). We found that the Vivado hardware file used before (the old .xsa) differs from the proven boot loader in exactly 2 values:

RegisterProven boot loaderOld Vivado fileMeaning
0xF800_60440x0F6666660x0FF66666Row address bit 14 used or not: 15 row bits = a 1 GB map (4 Gbit chips), 14 row bits = a 512 MB map (2 Gbit chips)
0xF800_60140x0004285B0x0004159BtRFC refresh time: 161 clocks = 302 ns (4 Gbit chips need 260 ns) or 86 clocks = 161 ns (2 Gbit chips need 160 ns)
What this means for your board The proven boot loader is set up for the bigger 4 Gbit chips that the schematic lists (MT41K256M16, 1 GB in total). Your board actually has 512 MB of real memory (2 Gbit chips): a read-only test on the running board showed that every address above 512 MB mirrors the one 512 MB lower, and U-Boot's own memory test also finds 512 MB. The 1 GB setup still works on 2 Gbit chips (the extra address line is simply not connected, and a longer refresh time is always safe), so the same boot loader runs on both board versions. The old Vivado file was set up exactly for 512 MB, which is also correct for your board. (An earlier version of this guide said the Vivado file reached only 256 MB and caused the PetaLinux problem; that was wrong. Why that old PetaLinux card did not start is not known.)
