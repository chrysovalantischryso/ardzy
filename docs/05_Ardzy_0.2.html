2. FPGA without Vivado

The Build FPGA button now runs a toolchain that lives inside the app. Nothing else needs to be installed.

PartWhat it isLicense
Yosys 0.66turns Verilog into Xilinx cells (LUT, FF, block RAM, DSP, IOBUF, PS7)ISC
nextpnr-himbaechel 0.11.1 (Xilinx)places and routes them on the XC7Z010; reports the maximum clockISC

How it was checked The frames made by Ardzy's fasm2bit were compared with Project X-Ray's own tool: 2952 frames, every bit the same. Then every part of the chip was measured on the real board by designs that test themselves (projects\fpga_selftest: 18 of 18, projects\fpga_ramtest: 11 RAM shapes, 3 runs each) and the pin-control design by pc_app\tests\pin_control_test.py: 10 of 10.

Five fixes inside nextpnr (all in pc_app\fpga\nextpnr_ardzy.patch)
  1. Pins: one bit per pin (ZINV_T1) was left out, so every output enable was upside down.
  2. Device DNA block could not be placed.
  3. LUT RAM (RAM64X1S): the packer crashed ("net already has a driver").
  4. Block RAM at width 1 and 9: a RAMB36-only setting (BRAM36_*_WIDTH_1) was never written.
  5. Block RAM at width 9: the 9th bit of odd addresses was never written (the upper half takes it from a second parity input). Found by reading back thousands of words on the board: it also made 5 logic analyzer channels (j3[0], j5[1], j7[2], j9[3], board_id[3]) always read 0 in the first Ardzy 0.2 pin-control. Fixed and installed on the board; the 0.2 image and update carry the fixed design.
Also: block RAM writes in the first few clock cycles after the FPGA starts can be lost (normal for the chip): start a design's work after a short wait.

Rules for your own designs:

  • Name the top module top (or put {"top": "name"} in fpga.json).
  • Pins in an .xdc file, as in Vivado: set_property PACKAGE_PIN T11 [get_ports {j1[0]}] and an IOSTANDARD LVCMOS33 line. Wildcards like leds[*] work. Pull-ups: set_property PULLTYPE PULLUP [get_ports {...}].
  • The clock comes from the ARM: use ardzy_clock or ardzy_soc from the library (next chapter).
  • Vivado still works: Settings, FPGA build tool = Vivado (projects with build.tcl).

Timing is checked by nextpnr's model. Placement is random: when a try misses the clock speed or has a hold problem, the app tries up to 5 placements and keeps the best (the pin-control design: try 1 reached 94 MHz, try 2 114 MHz, so try 2 is used).

3. The Ardzy FPGA library

Vivado's IP blocks (processing system, AXI GPIO, interconnect) are not available without Vivado, so Ardzy has its own small library (pc_app\fpga\hdl). It is added to every build.

ModuleUse
ardzy_clockjust the clock (FCLK0, 100 MHz) and a reset, for designs that do not talk to the ARM
ardzy_soc #(N_CTRL, N_STAT)clock + up to 32 registers the ARM writes (0x4120_0000 + 4n) and 32 values it reads (0x4120_0080 + 4n)
ardzy_ps7the Zynq PS7 block with its AXI GP0 port, for advanced designs
ardzy_axi3_liteAXI3 from the ARM (bursts, IDs) to simple AXI4-Lite, one word at a time
ardzy_lite_muxone AXI4-Lite master to 2 slaves; any other address reads 0 instead of stopping the bus
ardzy_gpioGPIO with the same registers as Xilinx AXI GPIO, so old Python programs keep working
// a whole design: 4 LEDs set by the ARM, a seconds counter read back
module top (output wire [3:0] leds);
    wire clk, rstn;
    wire [63:0] ctrl;
    reg  [31:0] seconds = 0;
    ardzy_soc #(.N_CTRL(2), .N_STAT(1)) soc (.clk(clk), .rstn(rstn), .ctrl(ctrl), .status(seconds));
    assign leds = ctrl[3:0];
    // ... count seconds ...
endmodule
No more frozen board from a wrong address With Vivado's interconnect, reading an address no block answers stopped the ARM until the watchdog restarted it. The Ardzy library answers every address (0 for unknown ones).

4. Arduino C++ sketches

New project, template Arduino sketch (C++), or Examples. Write setup() and loop() like on an Arduino and press Upload.

16 examples come with Ardzy (all compile, checked on the board): Blink, BlinkWithoutDelay, Button, Fade, DigitalReadSerial, AnalogReadSerial, SerialEcho, SerialPlotter, Serial1Bridge, I2CScanner, ServoSweep, FanControl, Melody, PulseCounter, BootCounter, BoardInfo. Installed libraries add their own examples.

7. Arduino libraries

Libraries opens the Library Manager: search the official Arduino library list, Install (with the libraries it needs), Remove, or Add .ZIP. Libraries are kept in projects\libraries. Upload sends only the libraries a sketch includes. Wire, SPI, EEPROM and Servo are always Ardzy's own versions (made for this board).

Tested on the real board (installed with the Library Manager, compiled and run):

LibraryResult
Adafruit SSD1306 (+ GFX, BusIO)works OLED displays over I2C
Adafruit BME280, RTClib, LiquidCrystal I2Cworks I2C sensors, clocks, character LCDs
ArduinoJson, TinyGPSPlus, PID, AccelStepperworks (TinyGPSPlus decoded a real NMEA sentence)
DHT sensor library, OneWirecompiles and runs timing by software: may need retries
Adafruit NeoPixelcompiles WS2812 LEDs need sub-microsecond timing that only an FPGA block can give (planned)

Libraries written for one chip only (AVR registers, ESP32 radio, USB) do not work. Most libraries that use the Arduino functions, Wire, SPI and Serial do. The fast pin functions of the classic cores (digitalPinToPort, portOutputRegister, ...) are there too, as many Adafruit libraries use them.

11. Writing an SD card

  1. Put the microSD card in the PC (USB reader or built-in slot).
  2. In the app: SD card. Choose the image (the app finds Ardzy-0.2-sdcard.img.xz), the card, and the board settings.
  3. Write card, confirm the card's name and size. Windows asks for administrator permission (writing a whole disk needs it).
  4. The app writes, reads everything back to check it, and puts ardzy.txt on the boot partition.
  5. Card in the board, boot jumpers on SD (JP2 and JP4), power on. After about 2 minutes the app finds <name>.local.
Safety Only removable USB / SD disks from 1 to 256 GB are offered; the PC's own disks are never listed as writable. The writer checks the disk again right before writing (number, size, name) and stops if anything changed.

12. Safe system updates

System, Settings and update, Install update sends an update file (Ardzy-0.2-update.tar.gz) to the board. It brings a new kernel, packages and Ardzy files. A new kernel is never trusted blindly:

Tested in the emulator scripts\test_os2_qemu.sh starts the image, installs the release update and a good new kernel (tried, then kept) and then an update with a broken kernel: the board went back to the previous kernel by itself and reported it. Result on the released image: 18 checks passed, 0 failed. The emulator runs a U-Boot that keeps its settings in uboot.env exactly like the board (scripts\test_uboot_for_qemu.sh); the real board's U-Boot reads the same file (its network MAC address comes only from there).
A board that runs Ardzy 0.1 1.0 has no update service yet. The app sees that and sends the installer together with the update, as a one-off program that runs once on the board; then it reads the result back and removes it. The settings file ardzy.txt is created from the board's current settings (name, time zone, SSH), so nothing changes by itself. Restart the board to start 0.2 (as a trial, like any new kernel).

On the board by hand: ardzy update /path/Ardzy-0.2-update.tar.gz, then reboot. The status: System, Settings and update, or /var/lib/ardzy/update_status.
